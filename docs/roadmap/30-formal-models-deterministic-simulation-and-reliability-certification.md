# Phase 30: Formal Models, Deterministic Simulation, and Reliability Certification

## Commit goal

Prove the most important TaskForge invariants with model checking, deterministic simulation, and a published reliability certification suite.

## Why this phase exists

Once TaskForge grows workflows, placement, idempotency records, multiple backends, and autoscaling, ordinary tests will not be enough. The riskiest failures will live in interleavings: stale acks, lease loss, scheduler fencing, duplicate workflow barrier release, placement reservation loss, and replay of ambiguous external effects.

This phase raises the engineering bar from "well tested" to "specified, simulated, and continuously checked."

## Changes

### Write executable models for core protocols

Model critical protocols such as:

- reserve, lease extend, ack, nack, and reclaim
- retry and DLQ transition
- scheduler leadership and fenced delayed release
- workflow barrier release
- placement reservation lifecycle
- idempotency effect state machine

Use a tool such as TLA+, PlusCal, Alloy, or a small state-space checker where appropriate.

### Build deterministic simulation

Add an in-process simulation harness with:

- fake clock
- deterministic broker backend
- worker and scheduler actors
- crash, pause, partition, and delayed-message faults
- randomized but replayable schedules

Every discovered failure should emit a seed that can be turned into a regression test.

### Define invariants

Track invariants such as:

- stale delivery owners cannot complete newer work
- a workflow barrier releases each downstream node at most once
- a fenced scheduler cannot mutate delayed or recurring state after leadership loss
- resource reservations cannot go negative or leak forever
- effect records never move from committed back to prepared
- admitted work never exceeds configured hard dependency caps

### Publish reliability certification

Create a certification suite that runs:

- conformance tests
- model-derived regression tests
- deterministic simulations
- Redis integration failure injection
- race tests
- benchmark smoke tests

The suite should produce a human-readable report for releases.

## Tests

- Model check: lease ownership invariants hold over bounded failure interleavings
- Model check: scheduler fencing rejects stale control-plane writes
- Simulation test: randomized worker crash and retry schedules reproduce from seed
- Simulation test: workflow fan-in never double-publishes downstream nodes
- Release test: reliability certification report is generated by CI

## Acceptance criteria

- Critical concurrency protocols have executable specifications
- Deterministic simulation catches timing bugs that normal tests miss
- Release confidence is based on a repeatable certification suite, not informal confidence
